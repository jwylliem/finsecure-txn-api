1. Introduction

FinSecure Pay want to deploy their transaction validation API faster and with less manual steps. In this project I build a small Spring Boot API with a /health and a /validate endpoint, and a Jenkins pipeline that build, test, scan and deploy it to Amazon EKS. Prometheus and Grafana is used for monitoring and alert is sent by email.

4. Design decisions

  • The Deployment have 2 replicas so if one pod die the app still work.
  • Readiness and liveness probe use the Spring Boot actuator health endpoints.
  • The max amount and currencies are in a ConfigMap so they can change without rebuild the image.
  • Image tag is version + build number + git commit, e.g. 1.0.0-5-a1b2c3d.
  • Dockerfile is multi-stage so the final image only have the JRE and run as non-root user.
  • Nodes are t4g.medium (arm64) because my Mac build arm64 images.
  • Jenkins check GitHub every 2 minutes (poll SCM) because it run on my laptop and cannot receive webhook.

5. Security

  • SonarQube quality gate, Trivy dependency scan, Trivy secret scan and Trivy image scan run in the pipeline. HIGH or CRITICAL vulnerability fail the pipeline so the image is not pushed.
  • To test, I added commons-text 1.9 which have CVE-2022-42889 (critical). The pipeline was blocked. After upgrade to a fixed version it pass.
  • Passwords and tokens are stored in Jenkins credentials (loaded from a .env file not committed to git). The API key of the app is a Kubernetes Secret.
  • Jenkins use a separate service account that only can deploy in the finsecure namespace.

6. Recovery

  • If a pod is deleted or crash, Kubernetes create a new one automatically (shown in demo).
  • If the new version rollout fail, Jenkins run kubectl rollout undo. We can also rollback manually with the ROLLBACK_TO parameter.
  • If a test fail, the pipeline stop and nothing is deployed.

7. AI use case: AI for alert analysis

Problem: when an alert come in, the engineer need time to check logs and metrics to find the cause. AI (a large language model) can read the logs and alert and give a summary of the possible cause faster than a human.

Inputs: the alert from Alertmanager, recent pod logs, metrics from Prometheus and the recent deployments.

Benefits: faster troubleshooting, less time to recover, help junior engineers.

Risks: AI can give wrong answer, so human must check before taking action. Logs may contain customer data so it must be masked before sending to AI. There is also cost for using the AI service.

Integration: Alertmanager can send a webhook to a small service which collect the logs and call the AI API, then send the summary by email together with the alert.

8. Lessons learned and future improvements

  • Setting up Jenkins took the most time, a bit sian at first, but using JCasC helped to rebuild it quickly.
  • A test found a bug where a missing currency crash the validator, so unit tests are useful.
  • Future: add HPA for auto scaling, centralised logging (EFK or CloudWatch), more alerts, and GitOps with Argo CD.
